# Audio Bridge — протокол v1 (CONFIG v2)

Один дуплексный поток байт (TCP-сокет для Wi-Fi, пара bulk-эндпоинтов AOA для USB, RFCOMM-сокет для Bluetooth — все дают
надёжный упорядоченный байтовый канал, поэтому протокол одинаковый для всех трёх транспортов).

## Транспорты → как получается поток байт

| Транспорт | Как телефон достаёт ПК |
|---|---|
| Wi-Fi | ПК раздаёт Wi-Fi (Mobile Hotspot), телефон подключается к ПК напрямую: `TcpClient(pcIp, PORT)` |
| USB | **Android Open Accessory (AOA)** — без adb, без USB-отладки и без режима модема. ПК — USB-хост: находит телефон по VID, шлёт vendor-запросы 51 (версия протокола), 52 (строки: manufacturer/model/description/version/uri/serial = `AudioBridge`/`AudioBridge`/…/`1.0`) и 53 (старт) — телефон пересчитывается как `18D1:2D00/2D01`. ПК открывает у него интерфейс с парой bulk-эндпоинтов (через libusb + драйвер UsbDk), Android запускает приложение по `USB_ACCESSORY_ATTACHED` (`accessory_filter.xml` сверяет manufacturer/model/version), а оно открывает аксессуар через `UsbManager.openAccessory`. Поверх пары bulk-эндпоинтов — тот же протокол кадров, что и по TCP. ПК объявляет клиента только после первого принятого байта (приложение шлёт CONFIG сразу при открытии): пока приложение не открылось, аудио не пишется в пустоту. Тишина с телефона > 12 с (PING идёт каждые 3 с) = обрыв. Запись, кратная размеру пакета эндпоинта, завершается нулевым пакетом. |
| Bluetooth | Классический RFCOMM с фиксированным UUID `7c9f1a2e-4b3d-4c7a-9e1f-2a6b8d4c5e3f`. ПК слушает через 32feet.NET (`InTheHand.Net.Bluetooth`), телефон подключается через `BluetoothDevice.createRfcommSocketToServiceRecord(uuid)`. Требуется, чтобы устройства были предварительно спарены (Bluetooth pairing) в ОС. |

Порт по умолчанию: **57120**.

## Discovery (поиск ПК в локальной сети, только для Wi-Fi)

Адрес ПК в сети раздачи различается у разных пользователей/роутеров, поэтому вводить его руками не
нужно — телефон ищет сервер UDP-broadcast'ом на порту **45120** (сознательно ниже динамического
диапазона 49152+, который Hyper-V/WSL/Docker режут на крупные зарезервированные блоки под NAT —
порт оттуда может не забиндиться с `WSAEACCES`, так и произошло на 57121 при тестировании):

1. Телефон рассылает broadcast-датаграмму `ABDQ` (4 байта, ASCII) на широковещательный адрес своей
   подсети (вычисляется из текущего Wi-Fi IP/маски) и слушает ответы ~2 секунды.
2. Каждый запущенный сервер отвечает unicast-датаграммой:
   ```
   byte[4] magic = "ABDR"
   byte    hostnameLength
   byte[]  hostname (UTF-8)
   uint32  tcpPort (LE)
   ```
3. Телефон показывает список откликнувшихся серверов (имя ПК + IP, откуда пришёл ответ) — выбор
   одного из них подставляет host:port для Wi-Fi-подключения.

Работает только пока сервер запущен (Discovery поднимается вместе с TCP/Bluetooth-слушателями по
кнопке «Старт»). USB и Bluetooth в discovery не участвуют — там адрес не нужен.

## Формат кадра

Little-endian, без выравнивания:

```
byte    type      // 0x01 = AUDIO_PC, 0x02 = AUDIO_MIC, 0x03 = FORMAT (control), 0x04 = CONFIG (control), 0x05 = VOLUME, 0x06 = MEDIA, 0xFF = PING
uint32  length     // длина payload в байтах (0 для PING)
byte[]  payload    // см. ниже, в зависимости от type
```

Направление кадра однозначно определяется тем, кто пишет в сокет: ПК пишет AUDIO_PC/FORMAT,
читает AUDIO_MIC; телефон — наоборот. Явный `type` оставлен на случай будущего мультиплексирования
и для отладки (дампы трафика).

PING отправляется каждые 3 секунды, если за это время не было отправлено ни одного AUDIO-кадра —
используется для обнаружения обрыва соединения (read timeout на другой стороне).

## FORMAT — анонс формата (ПК → телефон, один раз сразу после коннекта)

Приоритет — максимальное качество на приёме (целевое устройство: Sony Xperia 1 IV). Поэтому формат
звука ПК **не фиксирован жёстко**, а анонсируется при подключении, чтобы телефон сконфигурировал
AudioTrack/декодер под реальный формат микшера Windows (обычно 48000 Hz, но у пользователя может
быть выставлено иначе в свойствах устройства вывода) — без даунсемплинга там, где это не требуется
кодеком.

```
uint32  sampleRate   // напр. 48000
byte    channels     // 1 или 2
byte    codec        // 0x00 = PCM_FLOAT32 (raw, lossless), 0x01 = OPUS
byte[2] reserved      // 0x00 0x00
```

## CONFIG — настройки с телефона (телефон → ПК, один раз сразу после коннекта)

Настройки живут в Android-приложении (UI), а не захардкожены на ПК — телефон сообщает серверу, что
ему нужно. PC читает ровно столько полей, сколько прислано (старый клиент с одним `bitrate` работает):

```
uint32  pcAudioBitrateBps    // битрейт Opus для потока ПК → телефон (только Bluetooth; применяется на лету)
uint32  maxRawSampleRate     // v2: максимальная частота, которую телефон готов играть без сжатия
                             //     (по умолчанию 48000: Sony Xperia 1 IV принимает 192 кГц-дорожку, но не проигрывает ни кадра)
byte    nameLength           // v2
byte[]  deviceName           // v2: UTF-8, имя телефона — показывается в списке клиентов на ПК
```

Если микшер Windows работает на частоте выше `maxRawSampleRate`, ПК ресемплирует raw-поток для этой
сессии (WDL, в FORMAT уходит уже сниженная частота). Сервер ждёт CONFIG до 1,5 с перед отправкой
FORMAT — иначе первый кадр ушёл бы на неподходящей частоте.

Битрейт для потока телефон → ПК (микрофон) настраивается локально в приложении и не требует
согласования — энкодер на этой стороне телефон создаёт сам. Микрофон по умолчанию **выключен**
(переключатель в приложении): телефон шлёт AUDIO_MIC только если пользователь это включил.

## VOLUME — синхронизация громкости (в обе стороны)

```
byte  level   // 0..100, % от максимума
byte  flags   // bit0 = mute
```

WASAPI loopback снимает звук **до** регулятора громкости устройства, поэтому ползунок Windows сам по
себе ничего не меняет на телефоне. Вместо этого он зеркалится: громкость выбранного для захвата
выхода Windows (`IAudioEndpointVolume`) шлётся телефону, а тот ставит громкость потока MUSIC; нажатие
кнопок громкости на телефоне (`VOLUME_CHANGED_ACTION`) шлётся на ПК и применяется к выходу.
Сразу после подключения свою громкость отправляет телефон — так ни одна сторона не «подпрыгивает».
Изменения, которые применила сама синхронизация, обратно не отражаются (окно подавления 500 мс).

## MEDIA — кнопка наушников (телефон → ПК)

```
byte  command   // 1 = пауза/воспроизведение, 2 = следующий трек, 3 = предыдущий
```

Пока идёт стриминг, приложение держит активную `MediaSession`, поэтому Android отдаёт ей кнопку
гарнитуры (одно нажатие — пауза/пуск, двойное — следующий, тройное — предыдущий). Телефон шлёт
команду, ПК нажимает соответствующую медиа-клавишу Windows (`VK_MEDIA_PLAY_PAUSE` и т.д.) — реагирует
тот плеер, который реагирует и на клавиатурную клавишу.

## Кодек и качество по направлениям/транспортам

| Поток | Транспорт | Кодек | Частота/каналы | Битрейт/точность |
|---|---|---|---|---|
| ПК → телефон | Wi-Fi, USB | **PCM Float32 raw** (без пересэмплирования) | нативный формат WASAPI-микшера (обычно 48000 Hz stereo) | lossless, бит-в-бит |
| ПК → телефон | Bluetooth (RFCOMM) | **Opus**, application=AUDIO | 48000 Hz stereo (ресемплинг только для BT-пути) | 320 kbps (максимум для стерео-музыки в Opus) |
| Телефон → ПК (микрофон) | Wi-Fi, USB | **PCM16 raw** | 16000 Hz mono | lossless в пределах 16-бит |
| Телефон → ПК (микрофон) | Bluetooth (RFCOMM) | **Opus**, application=VOIP | 16000 Hz mono | 32 kbps |

Кодек для микрофона фиксирован (голос, качество некритично), для системного звука — объявляется через
FORMAT-кадр и зависит от транспорта: Wi-Fi/USB всегда lossless, Bluetooth всегда Opus (RFCOMM Classic
физически не тянет несжатый стерео-поток с приемлемым запасом по джиттеру — реальная пропускная
способность часто ограничена ~1-2 Мбит/с).

**USB — сознательно lossless, а не Opus**: канал AOA — это USB 2.0 bulk (десятки МБ/с), с огромным
запасом. Raw при высоком sample rate микшера (192 кГц
float32 стерео ≈ 12 Мбит/с) трафик заметный, но для Wi-Fi/USB это не проблема. Если у тебя
в Windows выставлено 192 кГц, а слушаешь обычную музыку — формат устройства можно снизить в
«Звук → Свойства → Дополнительно» до 48/96 кГц: слышимой разницы нет, трафик падает в 2–4 раза.

**Правило декодера: `decode()` возвращает число _интерлейвнутых_ сэмплов (кадры × каналы)** — одно
и то же для всех кодеков. Раньше raw возвращал интерлейвнутое число, а Opus — число кадров, а
вызывающий код всегда умножал на число каналов: для raw в AudioTrack уходило вдвое больше данных
(вторая половина — нули), т.е. звук по Wi-Fi/USB играл вдвое медленнее с тишиной между кусками.
Покрыто тестами `CodecsTest` (Android).

## Тайминг и буферизация (откуда берётся задержка и как она ограничивается)

**ПК.** WASAPI loopback работает в event-режиме: пакеты ровно по 10 мс, в том числе в тишине
(опрос «по таймеру» в NAudio давал пачки по ~62 мс — чистая добавочная задержка + джиттер).
Из пакетов нарезаются чанки по 20 мс **по мере поступления данных**, не по таймеру (замер:
джиттер выдачи чанков std 0,5 мс против 7 мс на таймере, макс. интервал 21 мс против 33–156 мс). Если
WASAPI замолчит, движок синтезирует тишину в реальном темпе, чтобы буфер телефона не пересыхал.
Каждый клиент получает чанки через одну ограниченную очередь (15 × 20 мс) с одним писателем:
порядок и потокобезопасность Opus-энкодера гарантированы, а при затыке сети самые старые чанки
отбрасываются, и задержка не растёт без предела.

**Телефон.** Каждый принятый чанк пишется не «как придёт» в AudioTrack, а через джиттер-буфер
(`PlayoutBuffer`), который меряет заполнение по реальной позиции воспроизведения AudioTrack:
- *Предзаполнение:* перед первым чанком в очередь кладётся `buffer` мс тишины (по умолчанию 120 мс,
  настраивается ползунком в приложении), потом `play()`.
- *Недогрузка:* если аппаратура выпила всё — очередь добивается тишиной до цели (один небольшой
  провал вместо череды щелчков), а цель растёт на 40 мс: канал с большим джиттером (Bluetooth)
  сам подбирает нужную глубину.
- *Переполнение:* если очередь выросла больше чем на 160 мс выше цели (отправитель «убегает»
  вперёд), входящий чанк пропускается — задержка не ползёт вверх.
Покрыто тестами `PlayoutBufferTest` на симулированных часах (паттерны джиттера взяты из замеров).

Opus-кодек реализован через [Concentus](https://github.com/lostromb/concentus) (чистый C#/Java порт
референсного libopus, без нативных зависимостей и лицензионных ограничений) — одна и та же логика
кодирования на обеих платформах.

Чанк аудио — 20 мс (компромисс задержка/накладные расходы на кадрирование):
- PC audio raw: 48000 Hz × 0.02 с × 2 канала × 4 байта (float32) = 7680 байт payload (при 48 кГц; масштабируется под реальный sampleRate из FORMAT-кадра).
- Mic raw: 16000 Hz × 0.02 с × 1 канал × 2 байта = 640 байт payload.
- Opus-кадры — переменной длины (укладываются в тот же length-prefixed формат без изменений).

## Жизненный цикл соединения

1. Клиент (телефон) устанавливает соединение любым из трёх способов (для USB «соединение» — это то, что ПК перевёл телефон в режим аксессуара и приложение его открыло).
2. Обе стороны сразу начинают писать AUDIO-кадры по мере поступления аудио со своего устройства
   (без хендшейка — формат фиксирован).
3. При обрыве чтения/записи (исключение сокета, PING не приходит > 9 сек) соединение закрывается,
   сервер возвращается в режим ожидания нового подключения. Android-сторона показывает статус и
   пытается переподключиться (для Wi-Fi/USB — с задержкой 2 сек; Bluetooth сервер также слушает заново).
