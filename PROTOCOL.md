# Audio Bridge — протокол v1

Один дуплексный поток байт (TCP-сокет для Wi-Fi/USB, RFCOMM-сокет для Bluetooth — оба дают
надёжный упорядоченный байтовый канал, поэтому протокол одинаковый для всех трёх транспортов).

## Транспорты → как получается поток байт

| Транспорт | Как телефон достаёт ПК |
|---|---|
| Wi-Fi | ПК раздаёт Wi-Fi (Mobile Hotspot), телефон подключается к ПК напрямую: `TcpClient(pcIp, PORT)` |
| USB | На ПК выполняется `adb reverse tcp:PORT tcp:PORT` (по существующему adb-соединению через кабель). После этого телефон подключается к `127.0.0.1:PORT`, а adb туннелирует это на PC:PORT. Порт тот же самый, что и для Wi-Fi, но сервер **отличает** такого клиента от Wi-Fi по loopback-адресу — см. ниже, почему это важно для выбора кодека. |
| Bluetooth | Классический RFCOMM с фиксированным UUID `7c9f1a2e-4b3d-4c7a-9e1f-2a6b8d4c5e3f`. ПК слушает через 32feet.NET (`InTheHand.Net.Bluetooth`), телефон подключается через `BluetoothDevice.createRfcommSocketToServiceRecord(uuid)`. Требуется, чтобы устройства были предварительно спарены (Bluetooth pairing) в ОС. |

Порт по умолчанию: **57120**.

## Discovery (поиск ПК в локальной сети, только для Wi-Fi)

Адрес ПК в сети раздачи различается у разных пользователей/роутеров, поэтому вводить его руками не
нужно — телефон ищет сервер UDP-broadcast'ом на порту **45120** (сознательно ниже динамического
диапазона 49152+, который Hyper-V/WSL/Docker режут на крупные зарезервированные блоки под NAT —
порт оттуда может не забиндиться с `WSAEACCES`, так и произошло на 57121 при тестировании):

1. Телефон рассылает broadcast-датаграмму `ABDQ` (4 байта, ASCII) на широковещательный адрес своей
   подсети (вычисляется из текущего Wi-Fi IP/маски) и слушает ответы ~2 секунды.
2. Каждый запущенный сервер отвечает unicast-датаграммой:
   ```
   byte[4] magic = "ABDR"
   byte    hostnameLength
   byte[]  hostname (UTF-8)
   uint32  tcpPort (LE)
   ```
3. Телефон показывает список откликнувшихся серверов (имя ПК + IP, откуда пришёл ответ) — выбор
   одного из них подставляет host:port для Wi-Fi-подключения.

Работает только пока сервер запущен (Discovery поднимается вместе с TCP/Bluetooth-слушателями по
кнопке «Старт»). USB и Bluetooth в discovery не участвуют — там адрес не нужен.

## Формат кадра

Little-endian, без выравнивания:

```
byte    type      // 0x01 = AUDIO_PC, 0x02 = AUDIO_MIC, 0x03 = FORMAT (control), 0x04 = CONFIG (control), 0xFF = PING
uint32  length     // длина payload в байтах (0 для PING)
byte[]  payload    // см. ниже, в зависимости от type
```

Направление кадра однозначно определяется тем, кто пишет в сокет: ПК пишет AUDIO_PC/FORMAT,
читает AUDIO_MIC; телефон — наоборот. Явный `type` оставлен на случай будущего мультиплексирования
и для отладки (дампы трафика).

PING отправляется каждые 3 секунды, если за это время не было отправлено ни одного AUDIO-кадра —
используется для обнаружения обрыва соединения (read timeout на другой стороне).

## FORMAT — анонс формата (ПК → телефон, один раз сразу после коннекта)

Приоритет — максимальное качество на приёме (целевое устройство: Sony Xperia 1 IV). Поэтому формат
звука ПК **не фиксирован жёстко**, а анонсируется при подключении, чтобы телефон сконфигурировал
AudioTrack/декодер под реальный формат микшера Windows (обычно 48000 Hz, но у пользователя может
быть выставлено иначе в свойствах устройства вывода) — без даунсемплинга там, где это не требуется
кодеком.

```
uint32  sampleRate   // напр. 48000
byte    channels     // 1 или 2
byte    codec        // 0x00 = PCM_FLOAT32 (raw, lossless), 0x01 = OPUS
byte[2] reserved      // 0x00 0x00
```

## CONFIG — запрос битрейта (телефон → ПК, один раз сразу после коннекта)

Настройки битрейта живут в Android-приложении (UI), а не захардкожены на ПК — телефон сообщает
серверу, каким битрейтом кодировать исходящий Opus-поток (актуально только для Bluetooth; для
Wi-Fi/USB игнорируется, там кодек не Opus). Применяется через `OpusEncoder.Bitrate`/`setBitrate`
на лету, без пересоздания энкодера/сессии.

```
uint32  pcAudioBitrateBps   // желаемый битрейт для потока ПК → телефон (используется только если
                             // активный кодек этой сессии — Opus)
```

Битрейт для потока телефон → ПК (микрофон) настраивается локально в приложении и не требует
согласования — энкодер на этой стороне телефон создаёт сам.

## Кодек и качество по направлениям/транспортам

| Поток | Транспорт | Кодек | Частота/каналы | Битрейт/точность |
|---|---|---|---|---|
| ПК → телефон | Wi-Fi, USB | **PCM Float32 raw** (без пересэмплирования) | нативный формат WASAPI-микшера (обычно 48000 Hz stereo) | lossless, бит-в-бит |
| ПК → телефон | Bluetooth (RFCOMM) | **Opus**, application=AUDIO | 48000 Hz stereo (ресемплинг только для BT-пути) | 320 kbps (максимум для стерео-музыки в Opus) |
| Телефон → ПК (микрофон) | Wi-Fi, USB | **PCM16 raw** | 16000 Hz mono | lossless в пределах 16-бит |
| Телефон → ПК (микрофон) | Bluetooth (RFCOMM) | **Opus**, application=VOIP | 16000 Hz mono | 32 kbps |

Кодек для микрофона фиксирован (голос, качество некритично), для системного звука — объявляется через
FORMAT-кадр и зависит от транспорта: Wi-Fi/USB всегда lossless, Bluetooth всегда Opus (RFCOMM Classic
физически не тянет несжатый стерео-поток с приемлемым запасом по джиттеру — реальная пропускная
способность часто ограничена ~1-2 Мбит/с).

**USB — сознательно lossless, а не Opus, несмотря на то, что физически это туннель через adb
поверх USB (`adb reverse`), а не голый USB-линк.** У native-rate raw легко набегает 10+ Мбит/с
при высоком sample rate микшера — это заметно больше, чем нужно голосовому Bluetooth, и в теории
может не влезать в adb-канал при заметной его загрузке (например, если параллельно запущен
`adb logcat` или идёт `adb install/push` по тому же кабелю — оба используют один и тот же
USB/adb-транспорт и делят с ним пропускную способность). Если звук по USB рвётся, в первую очередь
проверь, не занят ли adb-канал чем-то ещё, а не считай это поводом переключать USB на сжатие.

Opus-кодек реализован через [Concentus](https://github.com/lostromb/concentus) (чистый C#/Java порт
референсного libopus, без нативных зависимостей и лицензионных ограничений) — одна и та же логика
кодирования на обеих платформах.

Чанк аудио — 20 мс (компромисс задержка/накладные расходы на кадрирование):
- PC audio raw: 48000 Hz × 0.02 с × 2 канала × 4 байта (float32) = 7680 байт payload (при 48 кГц; масштабируется под реальный sampleRate из FORMAT-кадра).
- Mic raw: 16000 Hz × 0.02 с × 1 канал × 2 байта = 640 байт payload.
- Opus-кадры — переменной длины (укладываются в тот же length-prefixed формат без изменений).

## Жизненный цикл соединения

1. Клиент (телефон) устанавливает соединение любым из трёх способов.
2. Обе стороны сразу начинают писать AUDIO-кадры по мере поступления аудио со своего устройства
   (без хендшейка — формат фиксирован).
3. При обрыве чтения/записи (исключение сокета, PING не приходит > 9 сек) соединение закрывается,
   сервер возвращается в режим ожидания нового подключения. Android-сторона показывает статус и
   пытается переподключиться (для Wi-Fi/USB — с задержкой 2 сек; Bluetooth сервер также слушает заново).
